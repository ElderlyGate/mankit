# store unfinished list|clear: the shared command for changes cut short

## Why
The store refuses another user's change to a key a cut-short change holds with `unfinished_change`, and the refusal names `<app> store unfinished clear <thing>`. Owner, 19 Nov (Q-E of the mankit#47 review): that command is a shared mankit piece, built once, so every app mounts the same one, as it does `config queue`.

## Changes
- `store unfinished list [<thing>]` and `store unfinished clear <thing>`, thing-first, mounted by every app with a store scope; built on `store.Scope.Unfinished` and `Clear` (SP3).
- `list` shows each mark: whose it is, the machine, the keys it holds, and this user's journal file when it is on this machine, plus this user's journals whose marks are gone (`Left`).
- `clear` shows the change and its journal first and asks for the thing's name, a change to the system itself (G-STACK-6, owner 19 Nov), never silenced by a remembered answer; it removes only the marks it showed, re-checked in their turns, and never puts anything back; the journal stays.
- Server routes beside the command (G-STACK-4, owner 19 Nov): `GET /api/store/unfinished` and `DELETE /api/store/unfinished/<thing>?id=…` through serve's change door, mounted by every app's server.
- The answer kinds go to contracts mankit/v1 first (contracts card), CLI and HTTP alike (ADR-S03).
